# LoveBind compatibility quiz and PayFast milestone

## Compatibility quiz v1
- A quiz is only available inside an active mutual match between two currently approved, adult-age-verified, photo-approved members. Blocking, unmatching or account suspension removes access immediately.
- One shared, immutable versioned quiz session per match. Concurrent starts and answers use the same PostgreSQL per-pair advisory lock as safety operations.
- Seven 1–5 reflection questions covering relationship intent, values, lifestyle, communication, conflict, future plans and practical distance.
- Each member edits **only their own answers** until both finish. Each answer is encrypted separately with AES-256-GCM and `LOVEBIND_QUIZ_ENCRYPTION_KEY`, never written in plaintext to `QuizAnswer.ciphertext`.
- The participant sees only their own values and the other person's completion count. Neither participant sees the other's individual answers.
- Both must complete seven answers before an explainable weighted alignment score is calculated; the same completed assessment is visible to both.
- The result indicates preference alignment, **not relationship success or safety**. No OpenAI calls are enabled in this release, and no AI-generated inferences are presented as verified facts.
- These question IDs and the rubric version are immutable after deployment. Update with a new version, not silent modifications to prior sessions.
- REST: `GET /quizzes/matches/:matchId`, `POST /quizzes/matches/:matchId/start`, `PUT /quizzes/matches/:matchId/answer` with `{questionId,value}`.
- Uses existing `QuizTemplate`, `QuizSession`, `QuizAnswer`, and `CompatibilityAssessment` Prisma models; **no new migration**.

## Deploy and test
1. Set a new, distinct 64-character hexadecimal `LOVEBIND_QUIZ_ENCRYPTION_KEY` on Render backend, generated by `openssl rand -hex 32`. Never share this with mobile or Vite. Preserve key material securely; rotation requires re-encrypting answers.
2. Keep `LOVEBIND_CHAT_ENCRYPTION_KEY` configured separately.
3. Staging with synthetic adult matches: send messages, open quiz, confirm two participants can respond independently, verify that only the progress count is visible to the other member, and that both see the same score after completion.
4. Validate failed authorization, duplicate starts, invalid answers, encrypted storage, missing keys, and block revocation via the mandatory integration and unit tests.
5. Rebuild/redeploy the mobile client and backend from the **same passing commit**.

## PayFast, when payments are implemented
**Selected provider: PayFast (South Africa).** Payment processing is deliberately not enabled in this quiz milestone. Do not create wallet credits from client-supplied payment statuses or from success-return URLs.

Implementation design:
1. Build fixed, server-side credit packages with transparent ZAR prices; compatibility score may provide a suggestion but must not itself authorize a charge.
2. Create a pending payment purchase with a unique merchant reference; generate a signed PayFast Hosted Checkout request on the backend using private merchant credentials and passphrase; start in PayFast sandbox.
3. Validate the PayFast Instant Transaction Notification (ITN) using required signature, source verification, verified PayFast payment status, merchant identity, merchant reference, amount and currency. Follow PayFast's current integration documentation at implementation time.
4. Complete credit issuance **only once** after verified successful ITN, inside an atomic transaction: unique provider transaction/reference, wallet balance update and an append-only ledger entry. Repeated or malicious ITN requests must never double-credit.
5. Never treat a browser redirect to a thank-you or cancel URL as proof of payment. Provide reconciliation and refunds; use the same ledger safeguards for date reservations/releases.
6. Add sandbox automated tests for signature, invalid amount, replay, forged ITN and cancellation before production PayFast credentials are configured.

The quiz's `suggestedCredits` is only a **nonbinding illustration**. Payment and date-booking UI must remain unavailable until the validated PayFast integration and user-consent flow are ready.
